# Read-only Dashboard Implementation Plan

**Goal:** Ship selected A layout connected to persistent Hub tasks.
**Architecture:** Independent static frontend consumes versioned read-only projection API in the existing daemon. No second Service instance; browser uses a separate expiring read-only session.
**Tech stack:** Python standard library, dependency-free ES modules and CSS. React was a candidate, not a requirement; native modules preserve independent frontend deployment without adding a mandatory Node build step.
**Spec:** ../specs/2026-10-23-dashboard-design.md
**Execution:** subagent-driven-development; user resumed development after selecting A.

## Constraints
No machine-specific paths or state in distribution. Dynamic executor names. Execution and verification states distinct. Never infer delegation from attempts. No management token in browser. No mutation controls. All remote text rendered as text.

## Contract
GET /dashboard/api/v1/tasks?limit=30&offset=0&q=&state=&agent= -> {items:[Task],next_offset:null|number}
GET /dashboard/api/v1/agents -> {items:[{id,modes:[]}]}
GET /dashboard/api/v1/tasks/{id} -> {task:Task,messages:[{id,role,text,source,completeness,timestamp}],relations:[{task_id,kind,agent,state}],criteria:[],artifacts:[]}
GET /dashboard/api/v1/tasks/{id}/events?after_seq=0 -> {events:[{seq,kind,data,timestamp}],next_seq:number}
Task={id,title,agent,state,verification_state,work_status,created,updated,workspace_label,mode}.
GET /dashboard/ serves static application. Data endpoints require dedicated HttpOnly session. Initial login uses one-use short-lived ticket generated by trusted local client, delivered via URL fragment; POST /dashboard/session consumes it, returns cookie; fragment removed immediately. POST /dashboard/ticket requires existing daemon bearer; returns {ticket,url}. Only loopback same-origin requests accepted, ticket exchange validates Origin. Tickets expire after 60 seconds; sessions after 8 hours. No broad cookie reuse with /work.
